## 先记住这条完整链路

```text
PUT 接收目标状态 active
  ↓ 请求线程内的 MySQL 短事务
查询当前关系；若已经是目标状态，直接返回
否则修改 post_like / favorite / comment_like
并写入 interaction_event，一起提交
  ↓ 接口返回；后续工作尚可能没有完成
processEvents 后台批量处理互动事件
  ↓ 另一个 MySQL 事务
从关系表 COUNT，覆盖 post / comment 的计数
登记 POST / USER 投影任务
按条件登记通知 Outbox
标记本批 interaction_event 已处理，一起提交
  ↓
processProjections 扫描 interaction_projection
POST：缓存版本更新并删除详情缓存，再刷新热榜
USER：从近 90 天有效互动重建画像，版本校验后替换 Redis
全部执行成功并提交，才标记对应投影完成；失败保留并重试
```

> [!warning] 三个阶段不能合并成一次事务
> 请求提交，只说明互动关系和事件已持久化；不代表计数已重算，更不代表 Redis 已刷新。MySQL 事务也不能撤销已经完成的 Redis 操作。这里依靠持久化任务、重试和可重复执行的更新实现最终一致。

## 01 点赞完整链路与事务边界

**问题：** 从用户点赞到刷新详情看到最新计数，讲清请求、关系写入、事件处理、计数与投影的完整顺序。

**复习优先级：★★★★☆**

**原回答节选：**

> 选用了 PUT 接口来接收一个点赞的目标状态……开启短线程来进行写表，写到 post 的 like 表……还会写入一个 outbound 的通知信息通知表。还有一个互动引发的投影事物表……在一个短事务中进行写入。
>
> 后台任务……用 Set……找到受影响的帖子 ID……覆盖写回那个 post like 表的点赞计数……有一个字段是 can，如果 can 字段是 false……删除帖子详情或者是日报的刷新。

**评价与修正：**

- 目标状态、事件批量处理、帖子 ID 去重、异步刷新这条主线已有印象。
- “短线程”应为**短事务**。请求线程同步完成事务，并非另起线程写关系。
- 请求事务主要修改关系表并写 `interaction_event`；Outbox 和投影任务在后台处理事件时登记。
- 点赞计数写入 `post.like_count`，不是 `post_like`。
- 投影字段是 `kind` 和 `pending`：`kind=POST/USER` 决定任务类型；`pending=true` 才是待执行。

**参考回答：**

> 请求用 PUT 设置点赞目标状态。服务端查询当前关系，状态相同就直接返回；需要变更时，在 MySQL 短事务中修改关系并写入持久化互动事件。后台批量读取事件，对受影响帖子去重，从关系表统计并覆盖计数，同时登记投影、符合条件的通知 Outbox，并标记事件完成。之后另一个后台任务执行缓存失效、热榜刷新和画像重建，失败则保留任务重试，因此关系、计数和 Redis 之间是最终一致。

**复习动作：** 不看上面的流程，口述三个阶段各自的输入、写表和完成条件。

## 02 PUT 目标状态与重复请求幂等

**问题：** 第一次点赞已经提交，但响应丢失。客户端再次发送 `active=true`，是否再次插入关系和事件？PUT 与联合主键分别解决什么？

**复习优先级：★★★★★**

**原回答：**

> 请求会正常发送，但是不会成功。请求会尝试写入 post_like 表……因为联合主键……会写入数据库失败，也不会写入 interaction_event 表……一起回滚。使用 put 接口是为了接受点赞状态，而不是点赞状态切换，但是这样可以规避什么，我不太了解。

**评价与修正：** 第一次已经提交成功的顺序重试，通常直接成功返回，不会再尝试插入。

```java
boolean present = ...; // 查询当前是否已经点赞
if (present == active) return active;
```

**目标状态与切换状态的区别：**

```text
切换接口：未点赞 → 第一次请求已点赞 → 重试又变成未点赞
目标接口：设置 true → 已点赞 → 重试设置 true → 仍然已点赞
```

**参考回答：**

> PUT 接收明确目标状态，避免重试将状态再次翻转。服务端先比较当前关系和目标状态，相同就直接返回，不修改关系也不重复产生事件。联合主键兜底防止重复关系；如果并发插入产生冲突，代码在事务回滚后重试整个事务，重新读取状态。幂等性来自这些业务逻辑，不是改成 PUT 就自动具备。

**边界：** 幂等不等于解决所有请求乱序。相同目标状态重复执行和不同目标状态交错到达，是两类问题。

**复习动作：** 分别讲清顺序重试、两个并发 `true` 请求、切换接口重试三种情况。

## 03 关系与事件为什么同事务

**问题：** `post_like` 插入成功，但 `interaction_event` 写入失败，会留下点赞关系吗？为什么两步同事务？

**复习优先级：★★☆☆☆**

**原回答：**

> 不会，因为 post_like 和 interaction_event 在同一个事务中……主要是为了保证原子性。

**评价：** 核心正确，但“原子性”后还需说明业务意义。

**参考回答：**

> 两步一起提交或回滚。如果关系提交了、事件却没有，后台就可能无法通过这次事件更新计数、缓存、热榜和通知。因此同事务保证每次成功的关系变更都有对应持久化事件，供后台继续处理。这个事务不保证 Redis 当场完成更新，后续仍是最终一致。

**复习动作：** 用“如果不放同一个事务，会出现……”补全理由。

## 04 为什么不在请求中直接更新计数

**问题：** 为什么不在点赞事务里直接执行 `UPDATE post SET like_count = like_count + 1`，而是后台合并重算？

**复习优先级：★★★★☆**

**原回答：**

> 不直接用 update 是为了减少 io 次数，减轻数据库负担，也能避免一些并发错误。现在的方案是后台任务……找到受影响的 post……读取对应的 post_like 表 count 覆盖写入 like_count。

**评价与修正：** 后台流程正确，主要理由应是**减少热门帖子计数行的锁竞争**。

- 单条 SQL 的 `like_count = like_count + 1` 是原子更新，并不会仅因并发就丢失加一。
- 大量用户更新同一个帖子计数，需要竞争同一行排他锁，请求可能排队。
- 请求不再更新公共计数行；后台对帖子 ID 去重，一批内同一帖子只重算一次。
- 系统还增加了事件写入和统计查询，不能笼统宣称总体 IO 一定更少。
- 这里减少的是请求路径上的**计数行竞争**，不能扩大为整个详情、浏览或数据库完全没有热点。

**参考回答：**

> 直接加一虽然是原子的，但热门帖子计数行会成为锁竞争热点。我把关系变更和事件写入放在请求事务中，后台按帖子合并任务，从关系表重算并覆盖计数，减少重复更新并支持安全重试。代价是计数有延迟，还需要处理任务积压、失败重试和统计查询成本。

**复习动作：** 必须说出“竞争哪一行”“批量减少了什么”“付出什么代价”。

## 05 先点赞再取消为什么重算计数

**问题：** 用户先点赞再取消，两条事件都没处理，后台最终如何更新计数？为什么不简单按事件加一、减一？

**复习优先级：★★☆☆☆**

**原回答：**

> 点赞数不变，两个事件没处理，但 post_like 表的新增和删除都已经完成了。没 +1 -1 是因为……将这两个事看成了同一件事——对同一个 post_id 产生影响的事件。

**评价与修正：** 对关系表当前状态的理解正确。“同一件事”应改为**对同一帖子合并重算工作，两条事件本身仍然独立存在**。

**参考回答：**

> 后台按 post_id 去重，再从当前关系表 COUNT。点赞和取消已经分别完成新增和删除，所以在没有其他变化时，两次操作对最终计数净影响为零。重算依据当前状态，重复执行不会重复累加；增量加减并非不能做，但需要额外保证每条事件不会重复影响计数。

**复习动作：** 区分“合并重算目标”和“删除、合并事件语义”。

## 06 计数更新与事件标记之间宕机

**问题：** 已执行计数 UPDATE，尚未标记事件完成就宕机，恢复后怎么处理？

**复习优先级：★★☆☆☆**

**原回答：**

> 这个后台任务中我开启了一个短事务，计数更新和事件完成标记都在里面，宕机时会保证原子性。

**评价：** 事务边界正确，需要补充提交前后的具体结果。

**参考回答：**

> 计数更新、投影登记、符合条件的 Outbox 登记及事件完成标记在同一个数据库事务中。提交前宕机，这些修改不提交，事务回滚后事件仍待处理；提交后宕机，这些结果已一起保存，正常扫描不会再次选中已处理事件。

**边界：** 已执行一条 SQL，不等于事务已经提交；不能只说“宕机保证原子性”而不区分提交状态。

## 07 Redis 不可用时投影如何恢复

**问题：** 计数事务与投影登记已经提交，但 Redis 不可用，缓存失效和热榜刷新怎么恢复？

**复习优先级：★★★★☆**

**原回答：**

> 通过重试机制，interaction_event 表记录状态，失败之后记录失败和重试次数和下次重试事件。Redis 恢复之后进行正常逻辑，Lua 脚本删除缓存再刷新热榜。

**评价与修正：** 重试思路正确，但这里保存待执行工作的是 **`interaction_projection`**，不是已经完成计数阶段的 `interaction_event`。

**参考回答：**

> 投影任务已持久化在 interaction_projection。执行 Redis 失败，不会把任务标记完成，任务保留 pending=true，并记录 attempts、next_retry_at 和 last_error。后台扫描到重试时间后重新执行。POST 任务通过 Lua 更新缓存版本并删除详情缓存，再刷新热榜；执行成功并提交后才标记完成。

**复习动作：** 对比事件表与投影表：分别记录什么工作、什么时候完成。

## 08 缓存删除成功但热榜刷新失败

**问题：** Lua 已删除详情缓存，但热榜刷新失败。MySQL 回滚能撤销 Redis 操作吗？为什么重复执行不会把数据弄错？

**复习优先级：★★★★★**

**原回答：**

> MySQL 事务不能回归 Redis 缓存。第二个问题不知道。

**评价：** 跨存储回滚边界正确，但缺少安全重试的依据。

**参考回答：**

> MySQL 无法回滚已经成功的 Redis 操作，所以保留投影任务重试。再次删缓存不会修改数据库业务数据；如果缓存已经重新建立，再次删除会增加重建成本，但不会重复点赞。热榜从数据库当前状态重新计算，用 ZADD 覆盖同一个帖子成员的分数，而不是重复累加，所以重试不会把同一次互动反复加分。

```text
ZADD 热榜 100 帖子ID → 分数为 100
重复 ZADD 热榜 100 帖子ID → 仍为 100

如果每次执行的是“原分数 +100”，重试才可能错误累加成 200。
```

**边界：** 缓存 UUID 版本会再次变化；热榜分数也可能因时间衰减而变化。这里强调业务结果能够重新收敛，不是所有底层值都完全不变。

**复习动作：** 用“删除可重复、成员覆盖、状态重算”解释重试安全性。

## 09 缓存版本如何阻止旧查询回填

**问题：** 为什么删除详情缓存时还要更换版本？只 DEL 会出现什么并发问题？

**复习优先级：★★★★★**

**原回答：**

> 缓存版本主要是防止写入的时候防止并发问题。第二个也不清楚。

**必须掌握的时间线：**

| 顺序 | 查询 A | 修改 B |
|---|---|---|
| 1 | 缓存未命中，查询到旧标题，暂未回填 | |
| 2 | | 数据库更新为新标题并提交 |
| 3 | | 删除缓存 |
| 4 | 将此前查到的旧标题写回缓存 | |

只 DEL 无法阻止第 4 步。解决链路是：

```text
查库前记版本 → 清缓存时换版本 → 回填时核对版本
```

- A 查库前拿到版本 V1。
- B 提交更新后，Lua 原子设置新 UUID 版本 V2，并删除缓存。
- A 回填时，Lua 发现当前 V2 不等于预期 V1，拒绝写入。
- 回填脚本的“比较版本与写入”也要一起原子执行，避免检查后、写入前再发生失效。

**参考回答：**

> 版本机制用于阻止更新之前发起的旧查询，在删除缓存后重新写入旧数据。查询先记录版本，失效时原子换版本并删缓存，回填时原子检查版本一致才写入，避免旧查询污染缓存。

**边界：** V1/V2 只是不同 token 的示意，详情缓存使用 UUID 相等校验，不是数据库递增版本。

**复习动作：** 遮住本页，自己画出 A 查旧值、B 更新、A 回填被拒的顺序。

## 10 回填被拒绝是否保证响应最新

**问题：** A 的旧结果被拒绝写入 Redis，是否意味着 A 本次返回给用户的一定是新数据？

## 11 逻辑过期与异步重建

**问题：** Redis 详情还在，但逻辑过期，1000 个请求同时访问。谁返回旧值、谁重建？重建失败怎么办？

**复习优先级：★★★☆☆**

**原回答：**

> 对于抢到锁的请求去查库异步重建，没抢到锁的去返回旧数据。

**评价与修正：** 抢锁主线正确，但**抢到锁的请求也返回旧数据**；它触发异步任务，不等待重建完成。

**参考回答：**

> 命中缓存但逻辑过期时，请求尝试获取重建锁。获得锁的请求触发异步查库重建，其他请求不重复触发；这些请求都先返回旧数据。锁有过期时间，其保护依赖锁有效，并不能无条件保证任意情况下都只有一个重建任务。

> [!warning] 本轮讲解曾修正的失败分支
> 前面曾笼统说“重建失败仍可持续读取旧值”。核对当前代码后，应修正为：异步重建抛出异常时，会调用缓存失效逻辑主动删除详情缓存。旧缓存并不保证一直保留到物理 TTL。之后请求可能进入未命中分支。

**复习动作：** 一定说明“获得锁的是请求，实际查库重建在异步任务中；请求本身仍先返回旧值”。

## 14 兴趣画像如何计分以及为什么重建

**问题：** 收藏一篇属于美食分类、带火锅和川菜标签的帖子，分类和标签如何得分？取消后怎么办？为什么从数据库重建而不直接增减 Redis 分数？

**复习优先级：★★★★☆**

**原回答：**

> 按照整个帖子分数写入每个分类和标签，存在 Redis 中。取消收藏后会刷新画像。不是 Redis 加减而是数据库重建，为什么这么设计我也不清楚。

**计分修正：** “帖子分数”应为**该用户在这篇帖子上的互动权重之和**，不是全站热度。

```text
点赞 +2；每条有效评论 +3；收藏 +4

只收藏该帖：美食分类 +4，火锅标签 +4，川菜标签 +4
点赞并收藏：这篇帖子的用户互动权重为 2+4=6
则所属分类和每个关联标签分别贡献 6，不在标签之间平分
```

**当前重建依据：** 近 90 天仍存在的点赞、收藏，以及状态有效的评论；只聚合可见帖子的贡献。分类和标签分别写入该用户的 Redis ZSet。

**为什么重建：**

- 根据当前有效关系重新计算，任务重试不会重复加分。
- 取消收藏后，这条关系不存在，其贡献自然不再进入重建结果；其他点赞、评论贡献仍保留。
- Redis 丢失后可从数据库恢复，不依赖 Redis 之前的累积分数是否正确。
- 同一个用户的高频变更可以合并为一次待执行重建。
- 代价是查询和聚合比单次增减更重，因此限定时间范围并合并任务。

**参考回答：**

> 我以数据库有效互动为依据，先按帖子累加点赞、评论、收藏权重，再把该帖权重贡献给所属分类和每个标签。后台合并 USER 任务，重算近 90 天画像并整体替换 Redis，便于处理取消、重试和缓存恢复，避免增量分数偏离当前关系，代价是重建查询成本。

**边界：** 90 天是重建时查询的窗口，不表示历史贡献每天到期就自动扣分；Redis Key 的 90 天 TTL 也不是每条互动独立过期。

## 15 为什么用 Lua 整体替换画像

**问题：** 删除旧画像并逐条写新画像有什么问题？为什么放在同一个 Lua 脚本？

## 16 画像版本校验如何拒绝旧结果

**问题：** 版本 10 的新画像已写入，版本 9 的旧结果随后才尝试写 Redis，原子替换本身能否阻止覆盖？

```text

```

|---|---|---|

|---|---|---|
| 详情缓存回填 | UUID token | 当前版本等于查库前记录的版本 |

## 22 每小时热榜任务为什么称为持久化

**问题：** 每小时任务直接改 Redis，还是先登记数据库任务？如何找到待重算或清理帖子？登记之后宕机怎么恢复？持久化与单纯 @Scheduled 有何区别？

**状态：待测，休息前最后一题，尚未作答。**

**参考回答（整理时依据当前源码补充，尚未进行独立回答）：**

> 每小时任务获得调度锁后，查询数据库中近 24 小时发布且可见的帖子，并读取 Redis 全站热榜已有成员，将两部分 ID 合并去重。新帖需要重算，榜中已有但已过期、隐藏或删除的帖子也需要检查清理。任务通过 projectionQueue.post 把工作登记到 MySQL 的 interaction_projection，而不是当场清空并重建整个榜。
>
> 后台 processProjections 扫描 pending=true 且已到重试时间的 POST 任务，先失效详情缓存，再读取帖子当前状态刷新热榜；仍符合资格就重新计算并覆盖分数，不符合就移除。成功执行并提交后标记完成，失败保留任务并记录重试信息。已登记工作不会因为应用进程宕机就消失，恢复后继续扫描。

**拆成三步记忆：**

1. **找目标：** 数据库近 24 小时可见帖子 ∪ Redis 全站榜已有 ID。
2. **记工作：** 向 `interaction_projection` 登记 `kind=POST` 的任务，同一目标可合并；更新 revision、pending 和重试状态。
3. **做投影：** 后台判断资格，ZADD 覆盖或 ZREM 移除；失败继续重试。

**@Scheduled 与持久化的区别：**

| 机制 | 解决的问题 | 单靠它不能保证什么 |
|---|---|---|
| @Scheduled | 到时间调用某段代码 | 不会自动把待执行工作保存到数据库 |
| interaction_projection | 保存已登记工作的目标、版本、待处理与重试状态 | 不等于每次定时扫描都已经成功完成登记 |

**边界：** 当前每小时扫描依赖 Redis 调度锁和已有榜成员读取；如果登记之前失败，或登记循环中途停止，不能宣称整轮工作已全部可靠保存。持久化保证针对的是**已经成功登记的任务**；尚未登记的目标需要后续扫描或其他触发补充。

**复习动作：** 下次优先独立回答本题，重点讲“定时触发”和“任务持久化”是两个不同机制。

## 最容易混淆的八组概念

| 概念 | 要分清的点 |
|---|---|
| PUT 与幂等 | PUT 表达目标状态；业务判断、约束和事务才落实幂等 |
| 关系与计数 | post_like 保存关系；post.like_count 保存聚合计数 |
| 事件与投影 | interaction_event 驱动数据库聚合阶段；interaction_projection 保存后续投影工作 |
| 原子性与最终一致 | 单个 MySQL 事务原子提交，不代表 Redis 同步完成 |
| 逻辑过期与未命中 | 前者有旧值、走重建锁；当前后者无旧值、直接查库 |
| 版本校验与互斥锁 | 前者拒绝不合版本的写入；后者减少重复重建，不能互相替代 |
| 空画像与零匹配 | 空画像触发回退；画像非空但候选全零仍走普通推荐 |
| 定时调度与任务持久化 | @Scheduled 决定何时触发；数据库记录决定已登记工作如何恢复 |

## 简历表述需要保留的边界

- 点赞和收藏的请求提交，不等于聚合计数、投影、Kafka 投递、通知落库同时完成。
- 重建锁只覆盖当前逻辑过期分支，不能声称完全消除所有缓存击穿。
- 详情版本校验防止旧回填，不保证每个在途请求返回最新数据。
- 画像重建按当前有效互动计算，不是直接对 Redis 做 +2/+3/+4 增量更新。
- “无兴趣回退”更准确地描述为：未登录或获取画像后画像为空；不是所有候选兴趣为零都回退，也不是缺 Redis 画像就必然回退。
- 24 小时按帖子发布时间判断；置顶独立处理；Redis Key TTL 不能替代成员清理。
- 热度时间衰减不等于防刷措施。
- 持久化投影保障已成功登记工作可恢复，不表示所有调度轮次永不漏执行。
