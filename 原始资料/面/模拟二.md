## 01 PUT 重试与目标状态

**问题：** 第一次“设置为已点赞”已经提交，但响应丢失。客户端重试，如何避免重复关系和重复事件？

**复习优先级：★★☆☆☆**

**原回答：**

> 因为 put 接口接收的是目标状态，所以不会产生多次提交得到非目标状态。如果响应丢失，会根据唯一索引用户 id 和 postid 查询 postlike 表，有记录就说明有点赞记录，不再重复写入，直接返回状态设置成功。

**评价：** 核心正确。这次能说明成功重试不是必然主键冲突，而是先查询状态、直接返回，相比上一轮有进步。

**参考回答：**

> PUT 接收目标状态，避免重试再次翻转状态。服务端按用户 ID 和帖子 ID 查询当前关系，如果已达到目标状态，直接返回，不修改关系，也不产生新的互动事件。联合主键兜底防止重复关系，但 PUT 与唯一约束本身不能替代业务状态判断。

**边界：** 幂等不代表不同目标状态的请求乱序也自动得到用户最后一次操作的结果。

## 02 两个点赞请求并发插入

**问题：** 两个相同请求同时查询到“未点赞”，随后都插入，其中一个因唯一约束失败，怎么处理？

**复习优先级：★★☆☆☆**

**原回答：**

> 失败回去重试，然后就会查到已经有记录了，就返回已经点赞的状态。

**评价：** 能指出重试后重新读取状态。还要补充事务回滚与有界重试，不能承诺任何错误都无限重试。

**参考回答：**

> 唯一约束保证最多一条关系。发生允许重试的冲突时，先回滚本次事务，再执行整个事务并重新读取关系。如果另一请求已经提交，就发现目标状态已满足，直接返回成功；持续失败超过请求侧重试限制，则抛出异常。

## 03 重试单条 SQL 还是整个事务

**问题：** 重试只针对插入 SQL，还是关系变更与事件登记所在的整个事务？

**复习优先级：★★★☆☆**

**原回答：**

> 这是一个短事务，包含对 postlike 表的写入还有一个互动表，这两个写入在同一个事务中，一起回滚，重试插入发现已经有了就返回状态。

**评价与修正：** 知道两次写入共同回滚，但“重试插入发现已有”应说成**重试整个事务，重新查询状态后决定是否写入**。

**参考回答：**

> 一个尝试包含校验、查询关系、比较目标状态、修改关系、写入互动事件。异常导致整个事务回滚；允许重试时重新执行整个事务，而不是在失败事务中继续补一条 SQL。若重新读取后已经达到目标状态，提前返回，不重复产生事件。

**源码边界：** 当前请求侧对 `DuplicateKeyException` 和 `TransientDataAccessException` 做有界重试；`attempt` 从 0 开始，到 3 仍失败时抛出，即首次尝试之外最多再重试 3 次。

## 04 先点赞再取消如何计数

**问题：** 点赞和取消都已提交，两条互动事件尚未处理，后台如何更新计数？

**复习优先级：★★☆☆☆**

**原回答：**

> 后台读到互动表的时候读取到受影响的帖子 id，去查对应的 postlike 表重新统计计数，覆盖写回帖子的点赞数。

**评价：** 流程正确，可以补充对帖子 ID 去重，以及没有其他变化时两次操作净影响为零。

**参考回答：**

> 事件用于定位需要重算的帖子，真实计数来自当前关系表。后台对一批事件涉及的帖子 ID 去重，再 COUNT 并覆盖计数。用户先点赞再取消，关系表已经完成新增和删除，两次操作的净影响为零。重复处理也不会重复累加。

## 05 COUNT 与写回之间又发生点赞

**问题：** 后台统计到 100，写回前又有一个点赞提交，随后把 100 写回。如何最终修正为 101？

**复习优先级：★★★★☆**

**原回答：**

> 会写回 100，但是计数不会少，只是会有延迟最终一致，后台任务会在本次任务完成后，在固定时间后再次查库重新计数。

**评价与修正：** 短暂旧计数的判断正确，但“下一次定时会重算”需要具体触发依据。当前后台不是每轮重新统计所有帖子。

**参考回答：**

> 新点赞提交时也会登记新的持久化互动事件。如果它不在本批读取范围内，就保持未处理，下一轮扫描到它后再次驱动该帖子计数重算。因此可能暂时写回 100，之后修正为 101。关键是不能把新事件误标完成，否则缺少后续重算的触发。

**边界：** 如果本次 COUNT 已经包含新关系，下一轮再重算也没有副作用，因为是覆盖写，不是再加一。还需要任务能继续运行、失败能恢复，不能仅用“最终一致”四个字代替这些条件。

## 06 如何避免把新事件误标完成

**问题：** 本批读到帖子 A 的事件 E1，处理中新增了同帖事件 E2。怎么保证只完成 E1，不误完成 E2？

**复习优先级：★★★★★**

**原回答及追问过程：**

> 每次后台任务固定读取互动表的 500 条数据，找出影响的 postid 重新查表计数。
>
> 互动表有标记字段，标记已完成和未处理，查询的时候查询未处理，完成计数更新后，改成已完成，这些在同一事务中。
>
> 这个我还真不知道，你能告诉我吗？

**评价：** 批大小、状态筛选和同事务都没有回答“更新哪些事件”的问题，需要记住完成标记范围。

**参考回答：**

> 把本批读到的事件保存在 selected 集合里，处理结束只按这些事件的 ID 标记完成。E2 没被本批读到，就不在这个集合里，下一轮仍能扫描到。计数更新和本批标记在同事务中提交。

```sql
-- 示意：只完成本批实际读取的事件
UPDATE interaction_event
SET processed_at = CURRENT_TIMESTAMP(6)
WHERE id IN (本批事件ID);
```

**当前源码：** 实际实现遍历 `selected`，逐个执行 `WHERE id = event.id()`，不是必须使用 IN。

**不要混淆：**

| 机制 | 作用 |
|---|---|
| 同事务 | 计数与完成标记一起提交、一起回滚 |
| 按本批事件 ID 更新 | 不把没有读取的后来事件误标完成 |

不能仅按 `post_id` 把该帖子所有未处理事件全部完成。

## 07 事件已完成但缓存失效失败

**问题：** 计数已提交，互动事件已完成，但 Redis 缓存失效失败。原事件不再扫描，谁来补做？

**复习优先级：★★★★★**

**原回答：**

> 你给我讲一下吧。

**参考回答：**

> 数据库聚合阶段和 Redis 投影阶段使用独立的持久化完成状态。处理互动事件时，同事务更新计数、登记后续投影并标记事件完成。之后扫描投影表执行 Redis，成功才标记投影完成；失败保留待处理状态，记录重试信息。因此，即使原事件已完成，未完成的 Redis 工作仍可从数据库恢复。

```text
MySQL 聚合事务：
更新计数 → 登记 POST / USER 投影 → 标记事件完成 → 提交

Redis 投影阶段：
读取待处理任务 → 执行 Redis → 成功并提交后标记完成
                         └→ 失败：保留任务，之后重试
```

**源码核对后的具体表：** `interaction_projection`，字段包括 `kind`、`target_id`、`revision`、`pending`、`attempts`、`next_retry_at`、`last_error`。

**边界：** MySQL 回滚不能撤销已经执行成功的 Redis 操作，因此还需要重复删除、重算覆盖等可安全重复执行的操作。

## 08 重试次数上限与耗尽处理

**状态：学习补充，未独立作答。**

**主动提问：**

> 重试有次数上限吗，上限会怎么样？

**概念回答：** 重试策略可以持续退避，也可以有次数上限。达到上限应保留失败任务和原因，等待修复、人工重放，不能无记录丢弃，更不能当作成功。

**按当前项目区分：**

| 阶段 | 当前策略 | 耗尽或失败后的处理 |
|---|---|---|
| 点赞收藏请求短事务 | 首次之外最多重试 3 次，仅针对允许重试的异常 | 持续失败则抛出异常 |
| interaction_event 后台处理 | 未看到按 attempts 达上限停止的判断，失败保留事件并退避 | 后续扫描继续尝试 |
| interaction_projection 执行 | 未看到按 attempts 达上限停止的判断，失败保留任务并退避 | 后续扫描继续尝试 |
| Outbox 发送 Kafka | 累计失败达到 5 次 | 转失败状态，可管理员重置 |
| Kafka 消费 | 初次失败后，间隔 1 秒重试 3 次 | 转 DLT |
| 消费死信自动重放 | 自动重放计数最多 3 次 | 未解决且耗尽后转失败，可人工重放 |

**重要区别：** 互动事件和投影的退避间隔最长为 60 秒，这不是“最多重试 60 次”。调度间隔、任务到期时间和处理耗时共同决定实际再次执行的时间。

## 09 Redisson 后台重建是否先删缓存

**状态：学习补充，未独立作答。**

**主动提问：**

> 我记得有一个 Redisson 后台重建，它是在干啥，是删除缓存然后查库，重新写入缓存吗？

**参考回答：**

> 逻辑过期时仍然保留旧值，让当前请求先返回旧详情；另行提交后台重建任务。后台线程获取分布式锁，拿锁后再次检查缓存，仍需重建才查库，并在回填时校验版本。正常重建不需要先删旧缓存，否则其他请求就没有旧值可用，容易一起回源。

**当前源码的准确线程顺序：**

```text
请求发现缓存逻辑过期
→ submit：本实例按 postId 合并待执行任务
→ 提交到后台执行器；请求继续返回旧值
→ 后台线程 tryLock
→ 获锁后再次读取缓存
→ 若仍逻辑过期，或此时缓存已不存在，执行重建
→ 查库前记录版本，查库，校验版本并回填
→ 在获取锁的后台线程中释放锁
```

**本轮概念讲解需要精确化的地方：** 前面用“请求获锁后触发异步重建”帮助理解职责，但当前实现实际是**先提交异步任务，再由后台线程获取、持有并释放 Redisson 锁**。

`tryLock()` 没有指定固定租期，使用看门狗续期；不能因此宣称任何故障下都绝不会重叠执行。

**与变更失效区别：**

| 场景 | 做法 |
|---|---|
| 缓存存在但逻辑过期 | 保留旧值返回，后台重建 |
| 帖子变更导致缓存失效 | Lua 更换版本并删除缓存 |
| 完全未命中 | 当前请求路径仍直接查库，不由这个后台重建锁统一保护 |

重建异常时，当前重建方法会尝试删除详情缓存，不能保证失败后旧值始终保留。

## 10 重建锁与版本校验为何都需要

**问题：** 已经使用 Redisson 锁，为什么还要在失效时更换版本、回填时检查版本？

**复习优先级：★★☆☆☆**

**原回答：**

> 锁是保证查询到逻辑过期的旧缓存请求，只有一个请求去异步刷新重建缓存。版本校验是为了防止作者修改帖子更新缓存版本后，缓存回写的是逻辑过期查库查到的旧缓存。

**评价与修正：** 作用区分正确。被拒绝回填的是**此前从数据库查到的旧数据**，不应说成“查库查到旧缓存”。单次执行者的保护也依赖锁有效持有。

**参考回答：**

> 锁用于减少多个请求或实例重复重建，不能阻止作者同时修改数据库。版本用于识别这次查询期间是否发生过缓存失效，拒绝旧查询结果回填。锁控制重复工作，版本校验控制过时写入，不能相互替代。

**边界：** 拒绝缓存回填不会自动更新查询线程手里的对象，也不保证该次 HTTP 响应必然最新。

## 11 查库前还是查库后读取版本

**问题：** 重建任务在查询数据库之前还是之后读取版本？为什么顺序影响正确性？

**复习优先级：★★★★★**

**原回答：**

> 这个我不太清楚。

**错误顺序示例：**

| 顺序 | 查询任务 A | 修改请求 B |
|---|---|---|
| 1 | 从数据库查到旧标题 | |
| 2 | | 修改数据库并提交 |
| 3 | | 更换缓存版本为 V2，并删除缓存 |
| 4 | 此时才获取版本，拿到 V2 | |
| 5 | 携带 V2 回填旧标题，校验匹配而写入 | |

问题是：**旧数据拿到了新版本，版本校验也无法识别它。**

**正确流程：**

```text
A：查库前读取版本 V1
A：查询数据库，得到旧标题
B：数据库修改提交，再更换版本为 V2 并删缓存
A：携带之前保存的 V1 回填
Lua：当前 V2 与预期 V1 不同，拒绝写入
```

**参考回答：**

> 必须在查库前记录版本，回填时继续使用该版本，不能在回填前换成重新读取的新版本。查询期间若发生缓存失效，当前版本就变化，Lua 原子比较版本并写入，拒绝旧结果。

**复习口令：** 查库前记版本 → 清缓存时换版本 → 回填时核对版本。

**边界：** V1、V2 是示意 token。详情缓存是 UUID 相等校验；兴趣画像是数值 revision 比较，拒绝落后版本，两者规则不同。

## 12 点赞加收藏如何贡献兴趣分

**问题：** 一篇帖子属于美食，带火锅、川菜两个标签，用户先点赞再收藏，对三个维度分别贡献多少？

**复习优先级：★☆☆☆☆**

**原回答：**

> 都是 6 分。

**评价：** 本题回答正确。

**参考回答：**

> 点赞 2 分加收藏 4 分，得到用户在该帖上的互动权重 6。所属分类和每个标签都获得完整的 6 分，不在标签之间平分。

**边界：** 这是这篇帖子的贡献，不一定是整个画像的总分；其他帖子也可能对相同分类、标签贡献分数。这里也不是帖子热榜分数。

## 13 取消收藏后用户画像如何更新

**问题：** 用户随后取消收藏，怎样把该帖对美食、火锅、川菜的贡献从 6 分变为 2 分？

**复习优先级：★★★★★**

**原回答：**

> 取消收藏会写入投影任务表，然后按照任务要求，删除详细缓存，刷新热榜，热榜刷新计数是查库重建。

**后续：** 被追问用户画像如何更新后，要求查看代码讲解。

**评价与修正：** 回答的是帖子侧工作，遗漏用户侧画像。取消收藏请求也不是直接把所有工作写进投影表。

**当前源码链路：**

```text
请求短事务：删除 favorite 关系 + 写 interaction_event(active=false)
    ↓
processEvents：重算计数，登记 POST 和 USER 投影，标记事件完成
    ↓
processProjections 按 kind 分流：
    POST → 删除详情缓存，刷新热榜
    USER → rebuildStrict(userId, revision)，重建画像
```

| 投影类型 | target_id 的含义 | 任务内容 |
|---|---|---|
| POST | 帖子 ID | 详情失效、热榜刷新 |
| USER | 用户 ID | 分类和标签画像重建 |

后台收集用户 ID 不要求 `active=true`，因此取消收藏也会登记 USER 任务。

**参考回答：**

> 取消收藏先删除数据库关系并登记互动事件。后台处理事件时，为帖子和用户分别登记投影。USER 任务按近 90 天有效互动重建完整画像，已取消的收藏关系不再参与计算，最后通过带版本校验的 Lua 替换 Redis。不是直接在 Redis 减 4 分，也不是刷新热榜顺便更新画像。

**边界：** 接口成功不代表 Redis 画像已更新；重建全部有效互动，保留其他点赞、评论及其他帖子的贡献。

## 14 重建画像具体查询哪些表

**状态：学习补充，未独立作答。**

**主动提问：**

> 我想知道是怎么查数据库重建画像的，查到什么表？

**答案：** 查询 `post_like`、`favorite`、`comment`、`post`、`post_tag` 五张表。

| 表 | 查询条件或用途 |
|---|---|
| post_like | 当前用户，关系 created_at 在近 90 天；每条贡献 2 分 |
| favorite | 当前用户，关系 created_at 在近 90 天；每条贡献 4 分 |
| comment | 当前用户，created_at 在近 90 天且 status=1；每条贡献 3 分 |
| post | 查询上面涉及的帖子，过滤 status=1，并获取 category_id |
| post_tag | 查询仍然可见的帖子关联哪些 tag_id |

**计算分成三层：**

1. 根据三类互动按 post_id 累加，形成 `weightsByPost`。
2. 从可见帖子获得 category_id，把对应帖权重累加到 `categoryScores`。
3. 从 post_tag 获得标签，把对应帖权重累加到 `tagScores`。

**示例：**

```text
帖子101：美食分类，火锅和川菜标签；点赞+收藏 → 权重6
帖子102：美食分类，川菜标签；一条有效评论 → 权重3

画像：美食9、火锅6、川菜9

取消帖子101的收藏后：
帖子101权重变为2，帖子102仍为3
新画像：美食5、火锅2、川菜5
```

**注意事项：**

- 90 天筛选看互动记录创建时间，不是帖子发布时间。
- 同帖多条有效评论会分别贡献 3 分。
- 画像重建不靠读取 interaction_event 的增减事件算分，事件负责触发重建。
- 计算用分类、标签 ID，不需要查询 category、tag 表获取名称。
- Redis 丢失时可以从数据库重建；90 天窗口不会自动每天替每条贡献扣分。

**最后如何写 Redis：** 将分类与标签 Map 传给 Lua，比较数值 revision，拒绝旧版本，再替换 ZSet、TTL、就绪标记和版本。

## 15 超过24小时后积压热榜任务如何处理

**问题：** 非置顶帖子发布 23 小时 50 分钟时因大量点赞登记刷新任务，Redis 故障；20 分钟后恢复，帖子已超过 24 小时，积压任务应如何执行？每小时扫描和 ZSet TTL 分别起什么作用？

**复习优先级：★★★★★**

**原回答：**

> 有后台任务每小时定时刷榜。

**追问：** 积压任务可能先于下一次整点重试，应该使用旧分数还是重新读取当前数据，过期后对 ZSet 做什么？

**后续回答：**

> 我不知道，你来讲一下。

**评价：** 只回答了定期修正，尚未说明延迟任务自身如何避免错误回榜。

**参考回答：**

> 持久化任务保存刷新目标，执行时重新读取当前帖子并判断是否存在、可见、仍处在发布时间 24 小时窗口。题中已发布 24 小时 10 分钟，应从全站及对应分类榜 ZREM，而不是沿用故障前的高分 ZADD。仍符合资格的帖子才按当前计数和时间重新算分并覆盖。失败保留投影，后续重试。

**每小时任务的作用：** 没有新互动，时间也会继续流逝，因此主动登记刷新，重算衰减并清理过期成员。扫描合并：

```text
数据库近24小时可见帖子ID ∪ Redis全站榜已有成员ID
    ↓
逐个登记 POST 投影，再由持久化工作器执行
```

仅查询数据库近期帖子会遗漏已过期但仍留在 Redis 的旧成员，所以需要第二部分。

**TTL 为什么不够：** 26 小时 TTL 针对整个榜单 Key，不针对单个帖子。其他成员继续刷新还能延长整个 Key 的存活，因此不能靠 Key 过期按时移除某个帖子。

**边界：** 定时扫描保障的是持续修正；已成功登记的任务可恢复，但不是每轮扫描在任何故障下都一定完成登记。超过 24 小时也不等于 Redis 成员在那个瞬间同步消失，读侧筛选和后续刷新共同约束展示。

## 16 热榜降级与置顶复杂场景

**状态：待测。用户要求将后续问题和答案一起提供，本题没有独立回答，不评星。**

**问题：** A 发布 48 小时、已置顶、互动少；B 发布 1 小时、未置顶、互动多；C 发布 2 小时、热度最高但已隐藏。Redis 不可用时，如何响应某分类热榜，处理资格、置顶、评分和分页？是否给置顶帖极高分？

> [!faq]- 参考答案
> **1. 数据库筛选。** 查询可见帖子，满足“置顶或者近 24 小时发布”，叠加指定分类、标签等条件。A 可以作为置顶展示，B 符合普通资格，C 被隐藏后不能展示。
>
> **2. 置顶独立排序。** 先比较是否置顶，置顶之间按发布时间倒序，普通帖子按热度相关规则排序，不人为修改置顶帖的热度分数。
>
> **3. Redis 降级。** 数据库提供帖子与计数；读取 Redis 排名失败返回空名次集合，各帖无 Redis 名次，Java 比较当前计算热度与发布时间。
>
> **4. 排序后分页。** 当前实现取得全部合格候选后在 Java 排序，再截取请求页。不能先随意取数据库一页，再只对这一页排序，就声称得到全局热度排名。
>
> **5. 成本与边界。** 候选多时会增加查询、内存和排序开销；数据库聚合计数自身也可能有异步延迟。降级保障继续提供排序结果，不代表所有计数强一致。

**公式备查：**

```text
互动分 = 浏览×0.2 + 点赞×2 + 评论×3 + 收藏×4
热度 = (互动分 + 1) × exp(-发布小时数 / 12)
```

**面试口述版：**

> 先从数据库筛选可见且符合分类条件的帖子，普通帖限定近 24 小时，置顶帖独立保留并优先展示。Redis 不可用时，用数据库计数在 Java 中按相同公式计算热度，排序后分页。置顶通过独立排序实现，不污染评分。

**需要自测的边界：** 24 小时决定普通帖资格，衰减决定评分；ZSet 不会自动随时间改变 score；时间衰减不能单独防刷。

## 17 Outbox 租约与重复投递复杂场景

**状态：待测。已提供参考答案，未独立作答，不评星。**

**问题：** A 认领 Outbox 并发送 Kafka，Kafka 已确认，但 A 更新数据库状态前宕机。租约到期 B 重发，随后 A 恢复。如何防止旧状态回写、重复通知落库？能否保证只发送一次？

> [!faq]- 参考答案
> **1. 同事务保存发送意图。** 处理互动事件时，把符合条件的通知 Outbox、事件完成标记以及计数、投影登记放进同一 MySQL 事务，避免事件完成后没有留下发送任务。`NotificationEventPublisher.publish()` 要求已有事务，只写 Outbox，不直接发送 Kafka。
>
> **2. 原子认领。** 多实例可能扫描到同一记录，只有条件 UPDATE 成功者获得本次所有权。条件允许到期的待发送记录，或处理状态但租约已过期的记录；更新 processing 状态、独立 token 和两分钟租约。成功后按 token 重读，避免使用认领前的旧快照。
>
> **3. 条件回写。** 成功和失败更新都要求 id、processing 状态和 token 匹配。B 认领后 token 已变化，A 的旧 token 不能覆盖 B 的处理状态。
>
> **4. 承认重复发送窗口。** Kafka 成功与 Outbox 标记成功不是一个原子操作，A 宕机后 B 可能重复发送。token 保护数据库回写，并不能撤销或阻止已经发生的 Kafka 发送。
>
> **5. 消费落库去重。** 重发沿用该 Outbox 原 event_id；notification.event_id 唯一约束阻止同一事件重复落库。通知已提交但消费位点未提交时再次消费，也由此兜底。

**关键 SQL 条件：**

```sql
-- 成功或失败回写都限定当前所有者
WHERE id = ? AND status = 1 AND lock_token = ?
```

**租约与 token 的准确边界：** 租约到期允许其他执行者接管；当新执行者替换 token 后，旧 token 回写失败。不能说“时间一过期，原 token 无论如何都不能回写”，因为当前回写条件不直接判断 locked_until。

**Outbox 状态：**

| 状态 | 含义 |
|---|---|
| 0 | 待发送 |
| 1 | 处理中，持有租约 |
| 2 | 已发送 Kafka，不代表通知已经落库 |
| 3 | 发送失败达到限制，等待人工恢复 |

**面试口述版：**

> Outbox 保证发送意图与业务处理结果一起持久化，数据库租约协调认领，token 防止旧执行者覆盖新状态。但 Kafka 成功与数据库标记之间仍有故障窗口，所以允许重复投递，通过 notification.event_id 唯一约束实现消费落库幂等，不声称全链路严格只发送一次。

## 18 死信重放与终态保护复杂场景

**状态：待测。已提供参考答案，未独立作答，不评星。**

**问题：** 消费失败进入 DLT，自动与手动重放同时发生；一份消息已成功落库，但旧重放任务稍后返回失败，又收到延迟 DLT。如何协调重放、去重，避免把已解决记录改回失败或待处理？

> [!faq]- 参考答案
> **1. 失败分层。** Outbox 发送失败和 Kafka 消费失败不是同一阶段。消费初次失败后重试 3 次，仍失败转 DLT，死信消费者保存原事件、来源和失败原因。
>
> **2. 重放先认领。** 自动、手动重放都以数据库条件 UPDATE 认领租约，写入独立 token。有有效租约的记录不能被另一个正常执行者再次认领。手动重放也不能绕开正在执行的任务。
>
> **3. 保留原 event_id。** 重放重新发送到原通知主题，沿用原事件 ID；不能每次生成新 ID，否则通知表不能识别是同一事件。
>
> **4. 发送成功不等于解决。** 重放成功只代表再次交给 Kafka。消费者真正成功落库，或者发现通知已存在，才标记死信已解决并清空 token、租约。
>
> **5. 保护终态。** 重放回写要求记录仍处在可处理状态且 token 匹配。消费者已改成 resolved 并清空 token 后，旧失败回调无法把它改回失败，旧成功回调也不能覆盖解决结果。
>
> **6. 防止延迟 DLT 复活记录。** 重复写入已有死信时保留已解决状态。若成功消费时尚无死信行，后来 DLT 才建行，则根据 event_id 检查 notification 已落库记录，再把死信修正为已解决。

**消费死信状态：**

| 状态 | 含义 |
|---|---|
| 0 | 待处理 |
| 1 | 已重新发布，等待消费结果及后续检查 |
| 2 | 已解决 |
| 3 | 未解决且自动重放次数耗尽 |

**不要把两张表的状态 2 混淆：** Outbox 的 2 是 Kafka 已发送；死信的 2 是已解决。

**重试与恢复边界：** 自动重放最多 3 次，未解决且达到限制后进入失败状态，管理员可手动重放。人工操作不是无条件抢占有效租约；当前手动认领会重新设置重放计数，属于新一轮恢复尝试。

**面试口述版：**

> 消费重试耗尽后转 DLT 并持久化，自动和手动重放通过租约与 token 协调，沿用原 event_id，由通知唯一约束去重。消费成功才标记解决；回写检查 token 和可处理状态，重复或延迟 DLT 也不能把成功状态复活为失败，避免恢复状态倒退。
